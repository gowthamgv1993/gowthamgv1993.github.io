Terraform · GitHub Actions · GCP

Infrastructure by pull request

Problem
Every bucket, dataset or service account needed a platform engineer. Teams waited days. And every change was applied by someone running Terraform on their own laptop — no plan review, no record of who approved what.
Built
A deployment pipeline where the pull request is the interface. Engineers describe what they want by ticking boxes; the pipeline does the rest.
How
  • A PR template lists environments, modules and the action. The requester ticks what they need.
  • The workflow reads the PR body and turns those ticks into a build matrix.
  • Terraform plans each module and posts the full plan back into the pull request, split across comments so nothing is truncated.
  • The pipeline pauses until a reviewer ticks Approve in the PR, then applies and posts the result — success or failure — back to the same thread.
  • Authentication uses Workload Identity Federation: no service account keys anywhere.
Result
Teams request infrastructure themselves. Every change carries a plan, a named approver and an audit trail in one place. No local applies, no long-lived keys.

Terraform · config-driven architecture

Adding infrastructure by adding a file

Problem
A platform covering 27 kinds of resource across three environments. Every new bucket, dataset or permission meant writing Terraform, reviewing code, and waiting for a platform engineer. And because each environment had its own copy, the same fix had to be made three times — so the environments slowly drifted apart.
Built
Modules that take their inputs from JSON files instead of hard-coded values. The Terraform describes how a resource is built, once. The files describe what to build.
How
  • Each module reads every config file in its folder at plan time — no list to maintain, no wiring to update.
  • The files are templates. The project and environment are filled in at run time, so one file serves dev, staging and production instead of three copies that drift.
  • Adding a dataset means adding a six-line file. No Terraform is written and no module is touched.
  • Modules live in one repository and configs in another, so a fix to a module reaches every environment at once.
Result
Adding infrastructure became a data change, not a code change. Someone who has never written Terraform can request a resource correctly, and a reviewer reads six lines of JSON instead of a module diff. This is what makes the self-service pipeline above possible.

Python · Streamlit · Cloud Run · BigQuery · Terraform

Letting non-engineers document the data warehouse

Problem
Thousands of undocumented columns. The analysts knew what the data meant; the engineers had to type it in. Giving analysts write access to production metadata was not acceptable.
Built
A review tool with one firm rule: the app can never write to the warehouse. It produces a changeset; the existing Terraform pipeline applies it.
How
  • A web app behind an identity proxy — sign-in decides which environments you can even see.
  • Browse datasets, filter to columns that are still undocumented, write descriptions.
  • An optional AI draft writes the first version of each description — see the next project for how that was made safe.
  • Approved changes queue up, export as one spreadsheet, and a workflow diffs it against the previous version, rewrites the Terraform config and commits.
  • Everyone affected gets an email grouped by table, with the changes and the commit reference attached.
Result
The people who understand the data now document it themselves — and every change still lands through the same reviewed, audited path as any other infrastructure change.

Vertex AI · Gemini · Python

An AI assistant that cannot make things up

Problem
Writing thousands of column descriptions by hand is the job nobody ever gets to. A model could draft them in seconds — but a data catalogue containing invented facts is worse than an empty one, and engineers will not trust a tool they suspect is guessing.
Built
A suggestion engine where the model writes the sentence and the code supplies the facts. Every suggestion is a draft that a person edits and approves — there is no path that applies one automatically.
How
  • The answer shape is fixed. The model is given one field to fill and nothing else, so it simply cannot return headings, formatting or fragments of its own instructions. This replaced about 150 lines of text filtering that kept missing new ways of failing.
  • Examples are real, and always the same. Sample values come from the column itself — the most frequent ones — so the same column gives the same answer every run. An earlier version sampled at random and produced different examples each time.
  • The model never chooses the examples. It sees them only as context and is told not to quote them. Ordinary code picks which to show, by data type — smallest, middle and largest for numbers; earliest, middle and latest for dates. A value that isn't in the column cannot appear in the description.
  • Three ways to use it: write a new description, improve the one I just typed, or improve the one already there. Placeholders like n/a and null are treated as empty, so junk is never mistaken for real documentation worth preserving.
  • Failure is visible, never filled in. Retries raise the temperature each attempt — at zero a retry simply reproduces the identical failure, which is why some columns used to fail on every single run. After three attempts it reports the failure rather than inventing filler.
  • Two deliberate human actions — edit and apply, then add to the queue — before anything can reach the pipeline at all.
Result
The tedious 80% is drafted in seconds, and the human job becomes reviewing instead of authoring — without the catalogue ever showing a value that does not exist in the data.

Ansible · Jenkins · Jinja2 · AWS · GitLab

Building and bringing up a radio network from one job

Problem
A mobile base station is not one program. It is around fourteen separate codebases — boot firmware, the radio layers, the protocol stack, the management agent — that all have to be built at matching versions and started in the right order across several machines and radio units. Doing it by hand took most of a day, and when a test failed, nobody could say for certain which version of what had been running.
Built
A path from one triggered job to a running network: matching versions stamped across every repository, each physical lab described as data, and everything a failure investigation needs collected automatically.
How
  • One job stamps a coordinated, dated tag across every component repository through the source-control API, so a release is a single name that identifies the exact source of every part.
  • Each physical lab — several of them, with different hardware and layouts — is described as inventory data, not playbooks. Frequencies, transmit power, cell identities and which unit relays to which are values in files.
  • Where units relay wirelessly to each other, the number of hops changes per test — so the playbook is generated from the inventory instead of being written once per layout.
  • The Jenkins jobs are themselves code in a repository, and several jobs share one pipeline definition rather than each carrying a copy. Every merge request is built and deployed before it can merge.
  • After every run, each config file, binary, log and crash dump from every node is archived to S3 under a path keyed by job, release tag, timestamp and node — so a failure from two weeks ago can still be opened up.
Result
A full build and bring-up became a job you trigger rather than a day you spend. When a nightly run failed, the exact versions were already named and the evidence was already collected.

Jenkins · Groovy · Terraform · AWS

One shared library so every team deployed the same way

Problem
Dozens of services, each with its own hand-written pipeline. Every team had solved approvals, notifications and deployment order differently — and changing how deployment worked meant editing every pipeline separately.
Built
A shared pipeline library. A team's pipeline file became a few lines calling a standard shape; everything else lived in one place and was maintained once.
How
  • A small set of pipeline shapes — standard, infrastructure, incremental, downstream — so teams pick one rather than invent one.
  • One configuration file declares every component and what it depends on, so deployment order is worked out automatically instead of being remembered by a person.
  • Every infrastructure change runs plan → verify → approval in chat → apply. Nothing reaches an environment unreviewed.
  • Blue/green releases with DNS cut-over, so a bad version is switched away from rather than rolled back under load.
  • Secrets encrypted inside the repository; the branch decides which environment is targeted.
Result
A new service got a complete, working pipeline in a few lines. Changing how every team deployed meant changing one library, not forty pipelines.

Ansible · AWX · Packer · AWS

Configuration management for a mixed Windows and Linux fleet

Problem
Hundreds of servers across Windows, Debian and RedHat, all needing the same monitoring, security and application software. Installed by hand, so no two machines were quite alike and nobody could say what was actually on any given box.
Built
Around thirty reusable roles covering the full life of each piece of software, plus a deployment system built from small pieces that combine, driven from a web console so people who had never written Ansible could still run it.
How
  • Each role handles install, configure, start, restart and remove — separately for Windows, Debian and RedHat, behind a single entry point.
  • Application deployment split into small pieces — build, artifact, component, deploy, inventory, secrets — that combine, instead of one huge playbook.
  • Base machine images built with Packer, so servers start out consistent and configuration only handles what actually varies.
  • A web control plane gave a launch button to people who never touched a playbook — the same self-service idea as the Terraform work above, five years earlier.
  • Every role had its own pipeline and tests, so a change to a role was verified before it ever reached a server.
Result
A rebuilt server came back identical to its siblings. Rolling a new agent across the whole fleet became one run rather than a scheduled evening of manual work.

How I work
